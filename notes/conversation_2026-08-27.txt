SECTION 4: BINOMIAL CONFIDENCE INTERVALS
--------------------------------------------------------------------------------
- Explained why small-n (n=20) proportions like False-Alarm rate need Wilson score CIs
  instead of Wald/normal-approximation intervals (which break down at p near 0/1).
  Computed real Wilson CIs from detection_confusion_matrix.csv: e.g. FA=0/20 has 95% CI
  up to 0.161 — "0% observed" doesn't mean the true rate is provably near zero.
  Clarified: a wide CI doesn't mean the detector is bad, it means the measurement is
  imprecise at this sample size — the interval still excludes implausibly-bad values
  (e.g. 50%+ FA), and Recall (n=40, pooled jump+drift) has much tighter CIs than FA (n=20).

  level for G, variance for V) -> Stage-2 window-diff -> Stage-3 re-baseline against 20
  normal trials -> max(|score|) over post-onset windows = the final ML feature. Walked
  through a concrete example (hpmcounter3/D/jump/seed1: score climbs to 216.9 at iter 162).
- Explained exactly how TP/FP/FN/TN, Recall, and False-Alarm are computed for the ML
  models: RUN-level (one label, one prediction per whole trial), not window-level like the
  ensemble per-trial analysis (Section 6). Clarified precisely which data is used for
  training vs testing in the one-class LOSO loop (train_idx vs train_normal_idx filtering),
  and confirmed via code walkthrough that attack runs are NEVER used to fit the one-class
  models — only ever appear in test_idx.
- Confirmed precisely that ALL features (train and test, every mode) are built exclusively
  from t>=150 (post-onset) data, since build_feature_table() applies this filter before
  any LOSO split occurs — so pre-onset behavior cannot influence any ML decision, for any
  run, under the current design.
- Discussed real-world deployment gap: the current post-onset-only feature construction

  wouldn't have. Concluded the honest fix is a rolling-window redesign (score the last N
  windows continuously, reusing the already-causal per-window D/G/V scores) rather than a

  forward, not a currently-solved problem.
- Explained why one-class detection is genuinely different from the rule-based Q95
  threshold despite both being "unsupervised": rule-based detectors look at ONE counter at
  a time and combine via a hand-picked vote; Mahalanobis/LOF learn the JOINT shape of all

  threshold can't see. (User caught and corrected an earlier framing that used "doesn't

SECTION 7: NEW EVALUATION DESIGN — WINDOW-LEVEL FALSE ALARM FOR ENSEMBLE SCENARIOS
--------------------------------------------------------------------------------
- User designed a new, mixed-granularity evaluation for the three ensemble scenarios
  (I=any fires, II=majority, III=all three fire): TP/FN scored per RUN (did it fire at
  least once post-onset — since only "detected at all" matters operationally, not how many
  windows fired), but FP/TN scored per WINDOW (every pre-onset window is its own false-
  alarm opportunity, since false alarms are a recurring cost, not a single event). Ground
  truth: 0 before t=150, 1 at/after t=150, within each trial.
- Discussed and validated this design at length: run-level TP avoids penalizing a detector
  for correctly firing briefly rather than continuously; window-level FP gives far more
  statistical power (140 windows/trial vs 1 binary outcome) and matches the "point-
  adjustment" style evaluation used in some time-series anomaly-detection literature —
  flagged that this MUST be stated explicitly in the paper's methodology section to avoid
  looking like cherry-picked granularity.
- Built combined/ensemble_per_trial_confusion.py: computes per-trial (per counter, per
  attack type, per seed, per scenario) TP/FP/FN/TN/precision/recall/f1/false_alarm using
  this design, reusing scenario_fire_for_counter() from ensemble_firing_timeline.py for
  consistency. 600 rows (5 counters x 2 attack types x 20 seeds x 3 scenarios), saved to
  results/ensemble_per_trial_confusion.csv. Confirmed 289 windows/trial (140 pre-onset +
  149 post-onset), bounded by D_final's W=10 start offset.
- Computed average false-alarm ratio per (counter, attack_type, scenario) — averaged the
  per-trial false_alarm column across the 20 jump and 20 drift trials SEPARATELY (not

SECTION 8: DECISIVE INVESTIGATION — DOES ML "NOT WORK" BECAUSE IT FLAGS PRE-ONSET DATA?
--------------------------------------------------------------------------------
This was the most substantive methodological thread of the session. Sequence of findings:

1. User asked to explore an ML variant: train one-class models on normal-mode data's FULL
   289-window range (not just post-onset) instead of the standard post-onset-restricted
   149 windows, since normal-mode data has no attack timing to protect via oracle
   restriction (unlike attack-mode runs, which DO need the post-onset restriction to avoid
   scoring on non-attack behavior).
   RESULT: full-window training genuinely helped Mahalanobis (FA 0.30 -> 0.20, F1 0.930 ->
   0.952) and left LOF unchanged (FA=0.10, F1=0.976, identical numbers) — a clean win with
   no confound. Saved to results/ml_fusion_fullwindow_train_loso.csv.

2. User then asked to ALSO test jump/drift's pre-onset segment as an additional
   "should-be-normal" test case (ground_truth=0), alongside the existing post-onset
   (ground_truth=1) test case — using each attack trial's pre-onset segment as a second,
   separate test row. Built ml/ml_fusion_expanded_normal.py: 100 test rows total
   (20 normal_full + 20 jump_post + 20 jump_pre + 20 drift_post + 20 drift_pre), only
   normal_full rows ever used for training.
   RESULT: false-alarm rate spiked badly — Mahalanobis FA=0.583, LOF FA=0.500. Broke down
   WHERE the false positives came from (Mahalanobis): jump_pre 17/20 (85%), drift_pre
   14/20 (70%), normal_full only 4/20 (20%). Confirmed this is NOT a flaw in the ML models
   but a re-surfacing of the ALREADY-DOCUMENTED mode-dependent pre-onset noise-realization
   issue (Section 3/HaSS paper limitation 6) — jump/drift's pre-onset segment is generated
   via separate random draws in the test harness and is NOT actually statistically
   identical to genuine normal-mode data, despite representing the same "no attack yet"
   physical scenario.

3. Tried switching the feature aggregation from max(|score|) to mean(|score|), hypothesizing
   this would reduce sensitivity to rare single-window excursions.
   RESULT: mixed and mostly negative. On the standard (non-expanded) test set, mean() hurt
   LOF's recall (1.000 -> 0.925, missing 3 real attacks) and didn't improve Mahalanobis's
   FA. On the expanded test set, mean() made Mahalanobis WORSE (FA 0.583 -> 0.717,
   jump_pre/drift_pre flagged even more: 90%/95%) but helped LOF meaningfully (FA 0.500 ->
   0.267, jump_pre/drift_pre flagged less: 30%/40%), at the cost of recall dropping to
   0.925. Concluded mean() does not cleanly fix the underlying confound for either method.

4. User pushed back hard: "if ML was working it wouldn't flag anything pre-attack as
   attack" and "in a realistic setting, flagging before the attack has happened isn't good
   at all." Addressed this directly and honestly:
   - Distinguished the TEST-HARNESS ARTIFACT (jump/drift's pre-onset segment being
     statistically different due to separately-generated RNG draws per mode file) from a
     REAL DEPLOYMENT CONCERN (a real single physical sensor stream has no mechanism to
     "know" it will be attacked later, so pre-attack and never-attacked data are
     physically identical in real deployment — this confound has no real-world analog).
   - Clarified the CORRECT honest false-alarm number is the one measured against GENUINE
     normal-mode trials only (FA=0.10 for LOF), not the 85%/70% pre-onset-as-normal number.
   - User then asked "but rule-based never showed 85%/70% false alarms" — a sharp and
     valid challenge. Resolved DECISIVELY by testing: does the SAME "any window, any
     counter, any metric fires" aggregation, using ONLY the already-trusted rule-based
     D/G/V per-window flags (zero ML involved), produce the same pattern?
     RESULT: YES — normal 2/20 (10%), jump 15/20 (75%), drift 11/20 (55%). This proved the
     85%/70% ML result is NOT an ML-specific problem: aggregating "did anything fire
     anywhere across many checks" amplifies the same real, pre-existing data phenomenon
     regardless of whether the underlying detector is the ML model or the plain rule-based
     thresholds. The earlier low per-window-averaged FA numbers (Section 7) were low
     because they AVERAGE across windows (forgiving of rare firings); "did anything fire
     at all" is a much stricter aggregation that surfaces the same rare events as a much
     higher percentage.

5. User then asked: doesn't the ensemble voting design (majority/all-three-fire) ALSO bring
   down false alarms the same way? Tested directly using ensemble_per_trial_confusion.csv:
   for each trial, does ANY of the 5 counters have a pre-onset false positive, under each
   scenario?
   RESULT — decisive and very clean:
     Scenario I   (any one fires):  jump 15/20 (75%), drift 11/20 (55%)
     Scenario II  (majority, >=2):  jump  3/20 (15%), drift  2/20 (10%)
     Scenario III (all three fire): jump  0/20 (0%),  drift  0/20 (0%)
   Requiring simultaneous multi-metric agreement COMPLETELY ELIMINATES the pre-onset
   false-alarm problem for both jump and drift under Scenario III — the mode-dependent
   noise issue turns out to be a single-metric phenomenon; D, G, and V essentially never
   happen to agree with each other on the same noisy pre-onset moments.
   IMPLICATION FOR ML (proposed, not yet built at end of session): rebuild the ML features
   using the ensemble-agreement-filtered signal (e.g. only count a window if >=2 or all 3
   metrics fire there simultaneously) instead of each metric's max(|score|) independently,
   since the current ML features are built per-metric independently (closer in spirit to
   Scenario I) and likely inherited the over-flagging problem for that reason. This was
   proposed as the next concrete step but not yet implemented at the point this log was
   saved.
