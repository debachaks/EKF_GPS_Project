SECTION 2: CAN "CONSECUTIVE FIRING" BE APPLIED TO THE ML MODEL?
--------------------------------------------------------------------------------
- User asked why ml_fusion_expanded_normal.py (from the prior session — one-class models
  trained on normal-mode data, tested with jump/drift's pre-onset segment treated as an
  additional "should be normal" test case) still produces high false positives (85%/70%
  jump_pre/drift_pre vs 20% normal_full), and whether the same "require 3 consecutive
  windows to fire" trick that fixed the rule-based ensemble's false-alarm rate could be
  applied to the ML models the same way.
- Explained why it can't be bolted on as-is: the ML feature (max(|score|) per counter/
  metric, one number per whole trial) already collapses the entire time axis before the
  one-class model ever sees the data. A persistence/consecutive-window check needs a
  *sequence* of booleans over time to look at "did this stay elevated for 3 windows in a
  row" -- that sequence no longer exists once max() has reduced ~140-289 windows down to
  one scalar. Persistence has to be built INTO the feature before aggregation collapses
  time, not applied as a rule afterward.
- Connected this back to the actual reason ML was introduced in the first place (per the
  user's slide: "instead of a fixed voting rule, can a model learn the best way to combine
  all 5 counters together?"). Clarified these are two SEPARATE axes of the problem:
  combining ACROSS counters (the spatial question -- already working, since Mahalanobis/
  LOF do learn a joint 15-dimensional shape instead of a fixed vote) vs. aggregating WITHIN
  a single counter's own time series (the temporal question -- currently done badly, via a
  noise-sensitive max()). Fixing the temporal aggregation is a necessary complement to the
  "learn to combine counters" story, not a competing idea -- a smart fusion model can't
  fix noisy per-counter inputs on its own.

SECTION 3: IMPLEMENTING THE FIX — PERSISTENCE FEATURE
--------------------------------------------------------------------------------
Built adaptive_analysis_board_firmware/line_fitting/ml/ml_fusion_persistence_classifier.py:
replaces each counter/metric's feature -- max(|score|) -- with the LONGEST RUN OF
CONSECUTIVE WINDOWS where |score| exceeds that metric's own threshold H. Same idea as the
rule-based persistence fix, but computed as part of the feature itself, before the time
axis is thrown away. Built on the SAME expanded test design as ml_fusion_expanded_normal.py
(normal_full trained on the full window range; jump/drift split into _post [ground_truth=1]
and _pre [ground_truth=0] test rows) for an apples-to-apples before/after comparison.
Evaluation protocol, unchanged from prior sessions and used for every result below:
Leave-One-Seed-Out (LOSO) cross-validation -- hold out one seed's rows, fit the one-class
model (Mahalanobis / LOF) on the other 19 seeds' normal_full rows only, score the held-out
seed, repeat for all 20 seeds, pool every held-out prediction into one confusion matrix.
No attack labels are ever used to fit the model in any fold.

RESULTS:
  Expanded test set (100 rows: 20 normal_full + 20 jump_post + 20 jump_pre + 20 drift_post
  + 20 drift_pre), Mahalanobis and LOF (identical results for both, since the persistence
  feature is coarse/discrete enough that both land on the same decision boundary):
    Before (max feature):         FA=0.583 (Mahalanobis) / 0.500 (LOF), F1=0.696 / 0.727
    After (persistence feature):  FA=0.167 (both),                     F1=0.889 (both)
    Recall stayed perfect (1.000) throughout -- no cost to detection power.
  Breakdown by row_type (persistence feature): normal_full 0/20 flagged (0%, down from
  20%), jump_pre 5/20 (25%, down from 85%), drift_pre 5/20 (25%, down from 70%).

  Standard test set (60 rows: normal_full + jump_post + drift_post only -- this set does
  NOT include jump_pre/drift_pre at all, so it never measures the pre-onset-misclassified-
  as-attack scenario; user explicitly flagged and confirmed this distinction late in the
  session):
    Persistence feature: Recall=1.000, FA=0.00, F1=1.000 for BOTH Mahalanobis and LOF --
    the best result of the whole ML exploration, beating even the original max-based LOF
    (F1=0.976). Re-verified by rerunning live rather than trusting the earlier number.
    (Wilson 95% CI on FA=0/20 is [0.00, 0.161] -- flagged when directly asked about the
    "false alarm = 0" claim, not volunteered otherwise.)

SECTION 4: DIAGNOSING THE RESIDUAL 25%/25%
--------------------------------------------------------------------------------
- Broke down which specific (counter, metric, seed) combinations still produced false
  positives on jump_pre/drift_pre after the persistence fix. Finding: overwhelmingly
  concentrated in ONE counter -- hpmcounter3 -- across all three of its metrics (D, G, V),
  for a handful of specific seeds (6, 8, 9, 11, 12). hpmcounter4/5/8/10 contributed nothing
  to any of these 10 residual false positives. G_hpmcounter3 showed genuinely long runs
  (7-11 consecutive windows) for these seeds -- a real sustained stretch, not noise the
  persistence filter should catch.
- Consistent with hpmcounter3's role throughout the whole project as the noisiest of the
  5 usable counters (established in the 2026-08-27 session's pre-onset audit, and in
  today's Section 1 combined false-alarm plot).
- User asked (garbled by speech-to-text, interpreted as): if we drop hpmcounter3's features
  from training, does this go away? Tested precisely rather than assuming:
    - Dropping ONLY G_hpmcounter3 (14 features): barely helped -- FA still 0.15 (FP=9/60),
      because D_hpmcounter3 and V_hpmcounter3 still carry the same noisy signal on their
      own and the model just picks up on those instead.
    - Dropping ALL of hpmcounter3 (D, G, and V -- 12 features): dramatic fix -- FA dropped
      to 0.017 (FP=1/60), recall still perfect (1.000).
  Conclusion: the fix requires removing the whole noisy counter, not just one metric from
  it, since hpmcounter3 is noisy across all three of its detectors, not just G.
- Verified the standard (non-expanded) test set also stays perfect (F1=1.000, FA=0.00)
  with hpmcounter3 removed -- no regression, since it was already perfect there.
- User asked to confirm whether removing hpmcounter3 improves the model "overall" --
  clarified precisely that the standard test literally does not contain jump_pre/drift_pre
  rows at all (by construction, 60 rows only), so its FA=0.00 only ever measured false
  alarms on genuine normal runs, never the pre-onset-misclassification scenario. The
  expanded test is the only one that measures that, and it went from FA=0.167 (persistence
  feature, hpmcounter3 included) to FA=0.017 (hpmcounter3 excluded).
